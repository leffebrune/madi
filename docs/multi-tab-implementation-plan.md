# Madi 탭 기반 병렬 작업 구현 계획서

이 문서는 Codex의 `/goal`에서 실제 구현의 명세와 완료 기준으로 사용한다. 아래 확정 요구사항을 유지하면서 코드 수정, 회귀 검증, Windows GUI 빌드, 결과 보고까지 수행한다. 구체적인 클래스 이름과 분할 방식은 기존 코드에 맞게 조정할 수 있다. 제품 동작과 세션 점유 규칙은 변경하지 않는다.

## 1. 목표와 핵심 시나리오

한 앱 인스턴스에서 한 프로젝트 폴더를 대상으로, 기존의 **좌측 세션 목록 / 중앙 대화·입력창 / 우측 Work 창** 전체를 여러 탭에서 독립적으로 사용할 수 있게 구현한다.

각 탭은 세션 하나에 고정되지 않는다. 사용자는 탭 안에서 세션을 자유롭게 선택한다. 탭이나 세션을 전환해도 진행 중인 실행은 계속된다. 같은 세션을 다른 탭에서 중복으로 여는 것은 금지한다.

대표 완료 시나리오:

1. 프로젝트를 열면 탭 1에 기존 3열 UI가 표시된다.
2. 탭 1에서 세션 A를 선택하고 요청을 실행한다.
3. `+`로 탭 2를 열고 세션 B에서 다른 요청을 실행한다. A와 B는 실제로 동시에 진행된다.
4. 탭 1로 돌아와 세션 C를 선택한다. A는 계속 실행되고 B도 영향을 받지 않는다.
5. 탭 2에서 A를 선택하면 탭 1에서 사용 중임을 안내하며 선택을 거절한다.
6. 탭 1에서 A로 돌아가면 진행 중인 응답과 도구 상태를 확인할 수 있다.
7. B를 중지해도 A는 계속 실행된다. 완료된 대화는 각 세션에 정확하게 저장된다.

## 2. 확정 범위

### 반드시 구현할 사항

- 상단 탭 바에 탭 생성, 선택, 닫기를 제공한다.
- 탭마다 현재의 3열 UI와 기존 조작 흐름을 유지한다. 좌측·우측 패널을 기본적으로 숨기거나 다른 위치로 옮기지 않는다.
- 모든 탭은 같은 프로젝트 폴더와 같은 세션·Work 데이터를 사용한다.
- 탭별 세션 선택, 초안, 스크롤, 상세 펼침, 패널 너비를 분리한다.
- 서로 다른 세션의 실행과 취소를 분리한다. 실행 수명은 탭 선택 및 대화 화면의 수명과 분리한다.
- 세션 선택 및 새 탭에서 열기 경로 전체에서 다른 탭의 점유를 검사한다.
- 점유 검사는 UI와 별개로 앱 공통 계층에서도 강제한다. 실행 중이거나 저장·정리 중인 세션은 원래 탭의 점유를 유지한다.
- 공유 목록 갱신이 다른 탭의 선택, 초안, 스크롤을 변경하지 않도록 한다.
- 기존 세션 저장 형식, Work 관계, 모델 선택·인증, 명령어, 대화 삭제, 레거시 데이터 읽기 동작의 호환성을 유지한다.

### 이번 구현의 범위 밖

- 여러 프로젝트 폴더 동시 열기, 다중 창, 여러 앱 프로세스 사이의 점유 동기화.
- 탭 하나를 세션 하나에 고정하는 UI, 이전에 제안한 접이식 사이드바 중심의 재설계.
- Git worktree 도입, 파일 시스템 격리, 임의 Bash 명령까지 포함하는 새 파일 충돌 탐지 시스템.
- 모델/API 공급자 교체, 인증 기능 전면 재작성, 새로운 에이전트 기능.
- 앱 재시작 시 모든 탭·초안·진행 중 응답 복원, 자동 실행 재개, 백그라운드 서비스.
- 탭 고정·그룹·이름 변경·끌어서 창 분리 등 고급 탭 관리. 기본 넘침 처리는 포함한다.

프로젝트 파일은 공유한다. 기존 구조화된 파일 수정 도구의 잠금은 유지한다. 세션 점유 제어를 프로젝트 파일의 격리나 자동 병합 기능으로 설명하지 않는다.

## 3. 세부 동작 명세

### 3.1 앱 시작과 새 탭

- 프로젝트 선택/복원은 기존 흐름을 유지하고, 프로젝트를 연 뒤 탭 1을 하나 만든다.
- 탭 1은 기존 현재 세션 복원 규칙을 사용한다. 복원할 세션이 없으면 기존 새 대화 상태를 표시한다.
- `+`는 현재 탭의 Work와 모델 설정을 기준으로 기존 새 세션 생성 동작을 새 탭에서 수행한다. 현재 Work가 없으면 독립 세션을 만든다.
- 새 탭에서도 3열 UI가 즉시 보인다. 중앙은 새 대화이고 좌측 목록에서 기존 세션을 선택할 수 있다.
- 탭 번호는 앱 실행 중 생성 순서로 부여하고 닫아도 다른 탭 번호를 바꾸지 않는다. 탭 1, 탭 2 같은 표시 이름과 내부 `TabId`는 구분한다.
- 좌측 세션 메뉴에 `새 탭에서 열기`를 추가한다. 사용 중인 세션이면 빈 탭이나 중복 세션을 남기지 않고 거절한다.
- 새 탭 생성/세션 로딩 실패 시 기존 탭의 선택과 실행은 보존하고 오류를 해당 요청 위치에 표시한다.
- 마지막 탭을 닫으면 앱 종료로 이어지지 않고 새 대화 상태의 탭 하나를 남긴다. 기존 기록을 자동으로 삭제하지 않는다.

### 3.2 탭과 세션 탐색

- 탭마다 좌측 목록의 선택이 독립적이다. 한 탭의 선택이 다른 탭의 중앙/우측 화면을 바꾸지 않는다.
- 실행 중에도 탭 전환, 세션 선택, 새 탭 생성이 가능하다.
- A를 실행한 탭에서 C로 이동하면 A의 실행은 유지된다. 선택하지 않은 A의 응답·오류·사용량이 C의 대화에 추가되지 않는다.
- A로 돌아가면 저장된 성공 대화뿐 아니라 진행 중 응답, 도구 상태, 중지/실패 결과를 복원한다.
- 세션당 실행은 하나로 제한한다. 탭 전환과 무관한 앱 전체의 단일 실행 제한은 제거한다. 탭별 단일 실행 제한을 새로 도입하지 않는다.
- 입력창의 전송/중지는 현재 선택한 세션을 대상으로 한다. 다른 세션이 실행 중이라는 이유만으로 현재 선택한 대기 세션의 전송을 차단하지 않는다.
- 기존 Enter/Ctrl+Enter 입력 동작을 보존한다. 실행 중 작성한 초안은 별도로 보관하고 자동 제출하지 않는다.

### 3.3 실행 상태 표시

- 탭 제목 옆에 그 탭에서 실행/저장/정리 중인 작업이 있음을 표시한다. 여러 개면 개수를 표시한다.
- 기존 좌측 세션 행에 실행 상태와 다른 탭의 사용 여부를 작은 아이콘/텍스트로 표시한다. 기존 Work 묶음과 목록 구조를 유지한다.
- 백그라운드 실행 완료나 실패는 소유 탭/해당 세션에 미확인 표시로 남긴다. 자동으로 탭을 선택하거나 입력 포커스를 이동하지 않는다.
- 탭 순서는 실행·완료 이벤트로 바뀌지 않는다. 목록 메타데이터를 갱신할 때도 선택과 스크롤을 유지하고, 토큰마다 정렬/전체 재생성을 하지 않는다.
- 색상 외에 아이콘, 접근성 이름 또는 텍스트로 상태를 구분한다.
- 탭이 넘치면 현재 플랫폼 컨트롤의 스크롤/넘침 목록을 사용한다. 여러 줄로 늘려 기존 대화 영역을 계속 줄이지 않는다.

### 3.4 다른 탭에서 사용 중인 세션

- 다른 탭이 점유한 세션을 클릭하면 현재 탭과 세션을 유지하고 `탭 2에서 사용 중인 세션입니다`처럼 안내한다.
- WinUI 목록이 클릭 시 먼저 선택 표시를 바꾸는 경우, 거절 후 실제 선택뿐 아니라 목록의 선택 표시도 원래 세션으로 복구한다.
- 안내에 `해당 탭으로 이동`을 제공한다. 이 버튼을 선택했을 때만 소유 탭으로 이동한다.
- 소유 탭이 다른 세션을 보고 있다면, 이동 버튼은 소유 탭을 활성화하고 대상 세션을 선택한다. 이 선택도 같은 탐색 경로를 거친다.
- 같은 탭에서 자신이 실행 중인 세션으로 돌아가는 것은 허용한다.
- 같은 탭에서 이미 선택한 세션을 재선택하면 대화나 초안을 불필요하게 재설정하지 않는다.

### 3.5 탭 닫기, 앱 종료, 프로젝트 변경

- 실행이 없는 탭은 닫을 수 있다. 대화 기록은 삭제하지 않는다.
- 해당 탭의 진행 중 작업이 있으면 작업을 보여주고 `작업 중지 후 닫기` 또는 취소를 선택하게 한다.
- 닫기 확정 후 해당 탭에서 시작한 모든 실행에 취소를 전달하고, 하위 도구·서브에이전트와 저장/정리가 종료될 때까지 기다린다. 다른 탭의 작업은 취소하지 않는다.
- 정리 중에는 해당 탭의 신규 실행/선택을 막고 점유를 유지한다. 정리가 실패하면 성공적으로 닫힌 것처럼 처리하지 않는다.
- 미전송 초안/미저장 Work 편집을 닫기로 버리게 되는 경우 이를 명시하고 닫기 취소를 제공한다. 이 보호는 실행 중지 확인과 한 대화상자로 합칠 수 있다.
- 앱 종료는 모든 탭에 동일한 종료 절차를 적용한다. 현재 `MainWindow.OnClosing`의 즉시 동기 Dispose 경로를 비동기 정리와 재진입 방지에 맞게 변경한다.
- 프로젝트 변경은 앱 공통 동작이다. 현재 프로젝트의 모든 탭을 정리한 뒤 새 프로젝트의 탭 1을 만든다. 탭 하나의 프로젝트만 바꾸지 않는다.

### 3.6 공유 Work 및 삭제

- Work 지침은 같은 Work에 속한 모든 세션의 공통 데이터다. 실행 시작 시 사용한 지침은 그 실행이 끝날 때까지 고정한다.
- Work 저장 결과는 다른 탭에 반영한다. 수정하지 않은 편집기는 새 값을 따라가고, 수정 중인 편집기는 로컬 초안을 보존한다.
- Work 저장 시 읽었던 기준 버전과 현재 값을 비교해 다른 탭의 변경을 조용히 덮어쓰지 않는다. 충돌 시 초안을 유지하고 최신 저장본을 확인할 수 있게 한다. 대규모 병합 UI는 만들지 않는다.
- 다른 탭이 점유한 세션은 현재 탭에서 삭제하거나 대화 기록을 자를 수 없다. 소유 탭으로 이동하도록 안내한다.
- 자신의 세션도 실행/저장 중에는 세션 삭제 및 `여기부터 삭제`를 막는다. 사용자는 먼저 실행을 중지하고 종료를 기다려야 한다.
- Work 삭제는 자식 세션 전체에 대한 점유/실행 검사를 먼저 수행한다. 다른 탭의 점유 또는 진행 중 작업이 하나라도 있으면 전체 삭제를 거절하고 일부만 삭제하지 않는다.
- 삭제 검사와 실제 삭제 사이에 새 선택/실행이 들어오지 않도록 앱 공통 변경 조정을 적용한다.
- 삭제 후 대체 세션은 현재 탭에서 열 수 있는 세션 중 기존 정렬 기준으로 선택한다. 다른 탭의 세션을 빼앗지 않는다. 적합한 세션이 없으면 기존 새 대화 상태로 전환한다.

## 4. 세션 점유 규칙

공통 점유 관리자는 단순 선택 상태뿐 아니라 임시 예약과 진행 중 실행도 관리한다. 구현 자료구조는 조정 가능하지만 다음 불변조건을 만족해야 한다.

1. 한 `SessionId`의 소유자는 최대 한 `TabId`다.
2. 한 탭은 선택한 세션과 자신이 실행 중인 다른 세션들을 함께 점유할 수 있다.
3. 세션이 선택 중이거나, 실행/취소/저장/복구 중이거나, 유효한 선택 예약이 있으면 점유를 유지한다.
4. 선택·진행 작업·예약이 모두 없어졌을 때만 점유를 해제한다. 단순 UI 캐시나 초안의 존재만으로 점유를 계속 잡지 않는다.
5. 점유 확인과 예약 등록은 원자적으로 처리한다. UI의 비활성화만으로 중복 사용을 방지하지 않는다.
6. 실패·취소·오래된 비동기 결과는 자신이 획득한 예약/실행만 해제할 수 있다. 나중에 다른 탭/실행이 획득한 점유를 해제하면 안 된다.

세션 전환 A → B의 처리 순서:

1. 요청의 `TabId`와 탐색 세대 번호를 캡처하고 B의 점유를 예약한다. 다른 탭의 점유면 여기서 거절한다.
2. A는 선택 상태로 유지한 채 B를 준비하고 프로젝트/모델/존재 여부를 검증한다. 같은 탭의 진행 중 런타임이 있으면 그 상태에 재연결하고, 저장된 대화만 다시 읽어 실행 상태를 대체하지 않는다.
3. 요청이 여전히 최신이고 탭이 닫히는 중이 아닐 때 B 선택을 확정한다.
4. A의 선택 점유를 제거하되 A가 실행/저장 중이면 실행 점유를 유지한다.
5. B 로딩 실패·취소·요청 무효화 시 B의 임시 예약만 되돌리고 A의 상태를 보존한다.

느린 B 로딩 도중 C를 선택하는 경우 마지막 요청만 화면에 적용되어야 한다. 예약 잠금을 보유한 채 파일 I/O, 모델 호출, UI 디스패치를 기다리지 않는다. 실행 완료와 재선택/재실행이 교차하는 경우는 예약 토큰/세대/RunId를 사용해 오래된 해제를 무시한다.

권장 책임 분리:

- **WorkspaceCoordinator**: 한 프로젝트의 탭 등록, 활성 탭, 공유 메타데이터, 점유 관리자와 실행 관리자, 공통 이벤트를 소유한다.
- **SessionOwnershipRegistry**: 세션별 소유 탭, 선택 예약, 실행 점유, 삭제 중 보호를 관리한다.
- **SessionExecutionManager / SessionRuntime**: 세션별 원본 대화 상태, RunId, 실행 Task/CTS, 상태, 스트리밍 누적 결과와 완료 저장을 소유한다.
- **WorkspaceTabViewModel**: 탭 안의 선택과 명령을 관리한다. 기존 MainViewModel을 이 역할로 재사용/리팩터링해도 된다.
- **SessionViewState**: `(TabId, SessionId)`별 입력 초안, 제출한 입력, 스크롤, 상세 펼침과 표시 상태를 보관한다. Work 편집 초안은 `(TabId, WorkId)`별로 보관한다.

위 이름은 예시다. 책임과 수명은 지키되 필요 이상으로 서비스를 세분화하거나 동일 상태의 복사본을 여러 원본처럼 관리하지 않는다.

### 5.1 실행과 이벤트

- 긴 실행의 소유자를 활성 화면의 `await foreach`나 WinUI 뷰 수명에 두지 않는다. 앱이 Task를 보유하고 종료/오류를 관찰한다.
- 세션 실행 이벤트에 `SessionId`, `RunId`와 순서 또는 동등한 오래된 이벤트 판별 정보를 제공한다. 이벤트 범위가 탭인 경우 `TabId`, Work인 경우 `WorkId`를 명시한다.
- 공통 인증/설치/목록 이벤트와 세션 대화 이벤트를 구분한다. 단순 탐색 성공을 턴 완료로 처리하지 않는다.
- 스트리밍 텍스트, 도구/서브에이전트 결과, 사용량, 실패, 초안 복원을 모두 실행 소유 세션에 적용한다.
- 실행 상태 스냅샷 획득과 이벤트 구독 사이에 내용이 빠지거나 중복되지 않도록 버전/순서 기준으로 연결한다.
- 종료된 실행의 늦은 이벤트가 새 실행의 상태·초안·점유를 변경하지 못하게 한다.
- 명령은 실행 시작 시 대상을 고정한다. 비동기 대기 후 `_currentSession`을 다시 읽어서 다른 세션에 적용하지 않는다.
- 모델 설정, Work 프롬프트, 시스템 지침과 작업 디렉터리는 한 턴 안에서 일관된 값으로 사용한다.
- 현재의 약 40ms 스트리밍 버퍼링을 세션별로 유지하거나 동등하게 개선한다. 토큰마다 모든 탭/목록을 재생성하지 않는다.
- 비활성 탭의 콘텐츠를 누적하되 불필요한 Markdown 렌더링을 줄인다. 탭 전환 시 최신 표시 상태를 동기화한다.
- 실행별 취소는 하위 도구와 서브에이전트에 전파된다. 부모 열거가 취소되었다는 이유만으로 하위 Task가 종료되었다고 간주하지 말고 실제 정리를 관찰한다.

### 5.2 공통 서비스와 자원

- 같은 폴더의 ToolCatalog, 모델 카탈로그, 인증·공급자 구성, 저장소, 유틸리티 설치는 프로젝트 수준에서 공유하는 구성을 우선한다.
- 탭을 만들 때마다 `MadiAppFactory.CreateAsync` 전체를 복제해 별도 인증 흐름/설치/공급자 캐시를 만들지 않는다.
- 기존 공급자 캐시 잠금과 `SubagentRunner` 동시 실행 제한을 유지한다. 탭 수만큼 제한이 복제되어 실질적인 상한이 곱해지지 않게 한다.
- 앱 전체 모델 응답을 직렬화하는 잠금은 두지 않는다. 상태 변경·예약·파일 저장을 위한 짧은 잠금은 허용한다.
- OAuth 로그인은 공통 작업으로 중복 실행을 막는다. 로그아웃은 해당 인증을 사용하는 실행이 남아 있는 동안 거절하고 이유를 표시한다. 관련 없는 세션의 탐색은 막지 않는다.
- 테스트는 가짜 공급자/에이전트와 격리된 저장 경로를 사용한다. 검증을 위해 실제 사용자 대화나 자격 증명을 변경하지 않는다.

### 5.3 저장 및 복원

- 성공한 턴을 저장하는 현재 정책을 유지한다. 이번 목표를 미완료 응답 영속화 시스템 구축으로 확대하지 않는다.
- `AgentResponseCompleted`와 앱의 저장 완료를 구분한다. append·메타데이터 저장·복구가 끝나기 전에 실행 종료/점유 해제를 알리지 않는다.
- 현재 append 이후 metadata 저장 실패, append 중 취소, 저장 재시도 등에서 메모리와 파일이 어긋날 수 있는 경계를 처리한다. 성공/실패가 재현 가능한 하나의 턴 저장 계약을 만들고 중복 append를 막는다.
- 저장 구현은 기존 JSONL/메타데이터 및 레거시 읽기와 호환되어야 한다. 임시 파일/작은 복구 기록 등 필요한 최소 변경을 사용하고 일반적인 새 DB/이벤트 저장소로 교체하지 않는다.
- 프로세스가 저장 도중 중단되어도 다음 로드에서 확인 가능한 완결된 경계까지 복원하거나 명확한 복구 오류를 제공한다. 손상된 꼬리를 조용히 정상 대화로 취급하지 않는다.
- 기존 전역 파일 잠금은 우선 유지할 수 있다. 이것은 저장 연산의 직렬화이며 세션의 모델/도구 실행을 직렬화하지 않아야 한다.
- 현재 세션 포인터는 활성 탭에서 확정된 선택을 기준으로 한곳에서 쓴다. 백그라운드 완료, 비활성 탭 초기화 및 늦은 저장이 포인터를 덮어쓰지 않도록 순서/세대 검사를 적용한다.
- 앱 재시작 시 한 개의 탭 1과 마지막 활성 세션을 기존 방식으로 복원한다. 실행은 재개하지 않는다.
- 점유가 풀린 세션을 다른 탭이 수정한 뒤 원래 탭에서 다시 선택하면, 저장된 최신 대화/메타데이터를 읽거나 공통 원본의 새 버전을 사용한다. 이전 탭 캐시를 원본으로 저장하지 않는다.
- 탭 내 전환 시 초안·스크롤 보존은 필수다. 앱 재시작까지 이 UI 상태를 영속화하는 것은 이번 범위가 아니다.

## 6. 단계별 구현과 검증

각 단계 후 관련 검증을 수행하고 짧은 진행 기록을 남긴다. 순서는 위험을 낮추기 위한 기본안이며, 통합에 필요한 순서 조정은 가능하다. 최종 단계만 검증하고 앞 단계의 상태/점유 문제를 넘기지 않는다.

### 단계 0 — 기준선 확인

- 현재 브랜치와 사용자 변경, AGENTS 지침, 프로젝트 의존성, SDK/Windows GUI 빌드 조건을 확인한다.
- 기존 App/Runtime/Presentation 테스트를 실행해 선행 실패와 변경으로 인한 실패를 구분할 기준을 확보한다.
- 현재 3열 UI의 배치, 명령, 스크롤과 삭제 동작을 확인한다.
- 아래 기본 검증 명령을 현재 환경에 맞게 확정한다. 무관한 패키지/SDK 업그레이드로 문제를 회피하지 않는다.

### 단계 1 — 탭 컨텍스트와 점유 계약

- 안정적인 TabId, 탭별 선택 상태, 공통 점유/예약 API를 도입한다.
- 신규 선택, 같은 탭 재선택, 다른 탭 중복 선택, 실패 롤백, 빠른 연속 선택을 단위 테스트로 검증한다.
- 세션/Work 삭제 경로가 같은 점유 조정을 사용하도록 설계한다.

완료 증거: 병렬 선택 두 개 중 하나만 점유를 얻고, 실패·취소·오래된 요청 후 점유 누수가 없다는 결정적 테스트.

### 단계 2 — 세션 실행과 이벤트 분리

- 전역 실행 상태/취소 토큰을 세션 실행 상태로 옮긴다.
- 명시적인 SessionId/RunId로 실행·취소·이벤트를 연결하고 한 턴의 설정을 고정한다.
- 실행이 선택과 독립적으로 유지되며, 선택하지 않은 세션의 이벤트도 소유 상태에 누적되게 한다.
- 중복 실행 제한, 하위 작업 취소와 저장 완료 경계를 연결한다.

완료 증거: 가짜 스트리밍 에이전트를 이용해 A와 B의 실행이 실제로 겹치고, B 취소 후에도 A가 완료되며, 이벤트와 저장 결과가 분리됨을 검증.

### 단계 3 — 기존 3열 화면의 탭화

- MainPage의 프로젝트 선택/공통 기능과 3열 콘텐츠를 분리하고 기존 콘텐츠를 탭마다 재사용한다.
- 탭 생성·선택·닫기 및 `새 탭에서 열기`를 연결한다.
- 탭별 VM/뷰 상태와 중앙 타임라인 구독을 연결한다. 탭 전환 자체로 VM을 Dispose하거나 실행을 취소하지 않는다.
- 좌측 점유 안내, 소유 탭 이동, 탭/세션 실행 상태와 미확인 표시를 추가한다.
- 기존 3열 폭 조정, 포커스, 입력키, 도구 상세, Markdown 복사와 최신으로 이동 동작을 유지한다.

완료 증거: 탭 2개에서 서로 다른 세션이 진행되는 실제 3열 화면, 탭/세션 전환 후 초안·스크롤 복원.

### 단계 4 — 공통 데이터·실패·종료 통합

- 공유 목록/Work 변경의 갱신을 연결하고 타 탭 선택과 편집 초안을 보호한다.
- 삭제 검사, 현재 세션 포인터, 저장 실패 복구를 마무리한다.
- 탭 닫기, 앱 종료, 프로젝트 변경 시 비동기 정리와 점유 해제를 연결한다.
- 구독 해제, 타이머/버퍼, CTS 및 종료 Task 수명을 점검한다.

완료 증거: 실행 중 닫기/프로젝트 변경, Work 삭제 충돌, 저장 실패와 재시도 시 데이터·점유가 일관됨을 검증.

### 단계 5 — 회귀·패키징·문서 완료

- 아래 인수 시나리오와 기존 회귀 테스트를 수행한다.
- Windows GUI Release 게시를 수행하고 기존 단일 EXE 배포 조건을 유지한다.
- 실제 WinUI 화면의 기본 크기와 좁은 창에서 세 열, 탭 넘침, 포커스 및 닫기 동작을 확인한다.
- `ARCHITECTURE.md`에 최종 상태/실행/점유/수명 구조를 반영한다.
- 최종 변경 요약, 실행한 검증, 산출물, 남은 제약을 보고한다.

## 7. 필수 인수 시나리오

아래 항목이 최종 완료 판정의 기준이다. 비동기 테스트는 임의의 긴 sleep 대신 TaskCompletionSource, 제어 가능한 스트림/저장소와 제한 시간으로 순서를 결정한다. 기존 동시 입력 거절 테스트는 앱 전체 거절이 아니라 동일 세션 중복 거절을 검증하도록 수정한다.

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| A01 | 프로젝트 시작 및 `+` | 탭 1과 신규 탭에서 기존 3열 UI, Work/모델 상속, 독립 세션 |
| A02 | 탭 1 A 실행 + 탭 2 B 실행 | 첫 실행이 끝나기 전에 두 번째 실행 시작, 모두 정상 완료·개별 저장 |
| A03 | A 실행 중 같은 탭에서 C 선택 | A 실행 유지, C 화면에 A 텍스트/도구/오류/사용량이 섞이지 않음 |
| A04 | A로 복귀 | 스트리밍 본문, 도구·서브에이전트 진행, 초안, 스크롤 복원 |
| A05 | B만 중지 | B의 하위 작업까지 정리되고 A는 계속 실행 |
| A06 | 동일 세션 이중 제출 | 두 번째 실행 거절, 초안 보존, 저장 중복 없음 |
| A07 | 다른 탭의 선택 세션 열기 | 선택/새 탭 열기 모두 거절, 원래 화면 유지, 소유 탭 안내 |
| A08 | 화면에서 벗어났으나 실행 중인 A 열기 | 다른 탭의 선택 거절, 소유 탭에서는 재선택 허용 |
| A09 | 실행 완료 전 저장을 지연 | 저장/정리가 끝날 때까지 점유 유지 |
| A10 | A가 비선택이고 실행·정리 종료 | 점유 해제, 다른 탭에서 최신 대화로 열 수 있음 |
| A11 | 두 탭의 동시 점유 획득 | 정확히 하나만 성공, 패배한 요청의 탭/선택 유지 |
| A12 | 로딩 실패/취소/빠른 B→C 선택 | 이전 선택 또는 마지막 유효 선택 유지, 예약 누수·늦은 UI 적용 없음 |
| A13 | 늦은 완료/해제 이벤트 | 새로운 RunId 또는 다른 소유자의 실행·점유·초안 변경 없음 |
| A14 | 세션 생성/제목·Work 변경 | 모든 목록 갱신, 다른 탭의 선택·초안·스크롤 보존 |
| A15 | 두 탭의 Work 편집·저장 | 실행 지침은 고정, 다음 실행은 최신 값, 편집 충돌은 조용히 덮어쓰지 않음 |
| A16 | 다른 탭이 점유한 세션/Work 삭제 | 검사와 삭제 사이 경쟁까지 방지, 부분 삭제 없음 |
| A17 | 탭 닫기 취소 및 확정 | 취소 시 변화 없음, 확정 시 그 탭의 작업만 정리 후 점유 해제 |
| A18 | 앱 종료/프로젝트 변경 | 모든 필요한 작업의 정리 완료, 중복 종료/유령 점유 없음 |
| A19 | append 또는 metadata 저장 실패/취소 | 메모리·파일 불일치/중복 append 방지, 명확한 실패·복구 결과 |
| A20 | 활성 탭과 다른 탭 완료 순서 교차 | 복원 포인터가 실제 마지막 활성 선택을 가리킴 |
| A21 | 다른 탭 수정 뒤 이전 탭 재선택 | 오래된 캐시로 최신 대화를 덮어쓰지 않음 |
| A22 | 탭 생성/전환/종료 반복 | 이벤트 중복 구독·취소 토큰·종료 Task·점유 누수 없음 |
| A23 | 기존 기능 회귀 | 모델/provider 제한, 인증, 명령어, 삭제, 레거시 읽기, 서브에이전트 표시 유지 |
| A24 | 실제 GUI 및 Release 게시 | 3열 UI 유지, 탭 넘침/조작 확인, 기존 단일 EXE 게시 성공 |

권장 테스트 위치:

- `tests/Madi.App.Tests`: 점유, 실행 분리, 선택 예약, 삭제·종료·포인터·공통 상태.
- `tests/Madi.GUI.Tests`: 탭/세션 VM 상태, 초안, 이벤트 전달, 선택 유지, Work 편집 충돌 표시. 이 프로젝트는 플랫폼 중립 Presentation 테스트라는 점을 유지한다.
- `tests/Madi.Runtime.Tests`: 저장 실패/복구, 실제 파일 저장 계약, 런타임/서브에이전트 종료와 설정 스냅샷.
- 실제 WinUI 레이아웃/포커스/창 종료는 별도 GUI 스모크 검증으로 확인한다. 브라우저 시안이나 VM 테스트만으로 실제 앱 검증을 대체하지 않는다.

## 8. 검증 명령과 산출물

저장소 루트에서 실행한다. 이 문서는 아직 구현 전 계획이므로 아래 명령의 통과를 미리 주장하지 않는다.

```powershell
dotnet test tests/Madi.App.Tests/Madi.App.Tests.csproj -c Release
dotnet test tests/Madi.Runtime.Tests/Madi.Runtime.Tests.csproj -c Release
dotnet test tests/Madi.GUI.Tests/Madi.GUI.Tests.csproj -c Release
dotnet test tests/Madi.Services.Tests/Madi.Services.Tests.csproj -c Release
.\build-gui.ps1 -Configuration Release
```

단계별로 관련 프로젝트를 우선 검증하고 최종 시점에 전체 검증을 수행한다. 동일 코드에 대해 이미 통과한 검증을 이유 없이 반복하지 않는다. 변경으로 인해 필요한 테스트를 생략하지 않는다.

필수 산출물:

1. 요구사항을 실제로 동작시키는 앱/GUI/Runtime 코드 및 관련 테스트.
2. 최종 구조를 반영한 `ARCHITECTURE.md`.
3. `docs/multi-tab-implementation-progress.md`: 단계, 변경 파일, 검증 명령과 실제 결과, 실패/미검증 항목, 다음 작업을 간결하게 기록한다. 구현 시 생성한다.
4. Release 게시 결과와 실제 생성된 EXE 경로. 현재 스크립트의 기본 출력 디렉터리는 `artifacts/publish/madi-gui/release/win-x64`다.
5. 실제 GUI 검증 증거 또는 구체적인 실행 절차와 미검증 사유. 수행하지 않은 검증을 통과로 표시하지 않는다.

## 9. 자율 구현 지침과 종료 조건

- 이 문서를 다시 기획하는 것에 머무르지 말고 실제 구현과 검증을 수행한다.
- UI 모양, 클래스 이름, 파일 분리 등 통상적인 구현 선택은 기존 프로젝트 규칙 안에서 결정한다. 단계마다 승인을 받기 위해 멈추지 않는다.
- 사용자 변경을 보존한다. 무관한 리팩터링, 패키지 업그레이드, 자격 증명 변경, 실제 대화 데이터 정리, 외부 게시를 수행하지 않는다.
- 개발 검증에는 격리된 저장 디렉터리와 테스트 더블을 사용한다. API 호출을 전제로 테스트를 작성하지 않는다.
- 테스트가 실패하면 원인을 찾아 수정하고 해당 검증을 다시 수행한다. 기존 실패는 원인과 영향 범위를 기록한다. 실패를 제거하려고 테스트·경고 수준·필수 동작을 약화하지 않는다.
- 필수 검증에 필요한 SDK/빌드 도구/실제 GUI 접근이 없으면 실행 가능한 다른 작업을 진행하고 정확한 제약을 기록한다. 이 경우 미검증 항목을 완료 처리하지 않는다.
- 새 요구가 아닌 애매한 구현 세부사항은 합리적으로 결정하고 기록한다. 확정된 제품 동작을 바꿔야만 하는 문제가 발견되면 해당 충돌을 구체적으로 제시한다.
- 한 번의 응답이나 중간 빌드 성공을 전체 목표 완료로 취급하지 않는다. 진행 기록을 이어서 사용한다.

목표 완료는 **필수 제품 동작과 점유 불변조건 구현, A01–A24에 대한 검증, 관련 테스트와 Release 게시 성공, 실제 GUI 확인, 문서 갱신**이 모두 충족되었을 때다. 일부만 완료되었거나 필수 검증이 막혀 있으면 남은 작업과 필요한 조건을 보고하고 성공으로 선언하지 않는다.

최종 보고에는 변경 요약, 중요한 설계 결정, 실행한 검증과 결과, 실제 실행 파일 경로, 알려진 제한을 포함한다. 아직 필요한 사용자 조치가 있으면 실행 가능한 한 단계로 명시한다.

## 10. `/goal` 시작용 문구

현재 저장소에서 다음 문구로 시작할 수 있다. 다른 경로/체크아웃에서 실행한다면 파일 경로만 그 위치에 맞춘다.

```text
/goal G:\dev\madi\docs\multi-tab-implementation-plan.md를 먼저 읽고, 이 명세대로 Madi의 탭 기반 병렬 작업 기능을 실제 구현하라. 한 앱·한 프로젝트에서 탭마다 기존 좌측 세션 목록/중앙 대화/우측 Work UI를 유지하고, 탭 안의 세션 전환과 다른 세션의 병렬 실행을 지원하며, 같은 세션의 다른 탭 중복 열기는 원자적인 점유 검사로 막아라. 문서의 단계별 작업을 수행하고 docs/multi-tab-implementation-progress.md에 진행과 실제 검증 결과를 기록하라. 필수 인수 시나리오, 관련 테스트, Release 게시, 실제 WinUI 확인 및 ARCHITECTURE.md 갱신까지 완료하라. 통상적인 구현 선택은 자율적으로 진행하고, 필수 검증이 남아 있으면 완료로 선언하지 마라.
```

문서 구성은 목표·범위·검증·단계별 기록·종료 조건을 명시하는 [공식 Goal 사용 안내](https://learn.chatgpt.com/use-cases/follow-goals)를 참고했다. Madi의 제품 요구사항과 구현 내용은 이 프로젝트 코드와 본 대화에서 확정한 기획을 기준으로 한다.
